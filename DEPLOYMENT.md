## 2. Local setup (verified on Windows 11 with Docker Desktop)
```
npm install
npm run db:start           # first run pulls Docker images (several minutes)
npm run db:reset           # applies supabase/migrations
npm run build              # writes .env.local from the stack, builds, writes _headers and sw.js
node scripts/serve-out.mjs # http://localhost:3000
```
Tests: see `TESTING.md`. Stop with `npm run db:stop`.

Local gotchas learned the hard way:
- Edit `supabase/config.toml` or `supabase/.env` only while the stack is **stopped**, then start it again; changes made while it runs or pulls are ignored.
- Stray test servers can keep answering on a port and make a run meaningless. Find and stop them by command line, not by port number.
- `supabase/.env` and `.env.local` are git-ignored. `.env.local` is regenerated by `npm run build` and holds public values only; the Google secret belongs **only** in `supabase/.env` (local) or the Supabase dashboard (hosted).

## 3. Secrets and where they live
| Secret | Local | Hosted | Never in |
|---|---|---|---|
| Google OAuth client secret | `supabase/.env` | Supabase dashboard, Authentication, Providers, Google | the repo, the app bundle, `.env.local`, chat |
| Supabase service-role / secret key | CLI only (not used by the app) | dashboard only | the app, CI logs, the repo |
| Supabase URL and anon/publishable key | `.env.local` (generated) | environment variables at build time | (public by design) |
| Cloudflare login | `wrangler login` on the owner's machine | n/a | the repo |

The build guard `scripts/staging-env.mjs` refuses a hosted build if the public key is actually a secret key, or if the URL is local or not HTTPS (tested, including a mutation check).

## 4. Staging setup (not yet done)
**OWNER steps (need your Supabase account):**
1. Create a Supabase project named `tailorpro-staging`. Choose region **eu-west-3**. **Unverified:** that the free plan offers this region; if it does not, stop and tell me.
2. Note the **project reference** (Project Settings, General) and the **URL**, **anon/publishable key** (Project Settings, API). Never copy the service-role or secret key into the app.
3. Run `npx supabase login`, then in the repo `npx supabase link --project-ref <your-ref>` (replace the placeholder with your reference, without brackets).

**Then (I can run these once linked; none verified yet):**
4. Apply the database: `npx supabase db push`. Then confirm with the catalog checks (`supabase/tests/database/00_catalog.test.sql` can be run against the linked database with `npx supabase test db --linked`).
5. Apply the auth settings from `supabase/config.toml` to the hosted project. `config.toml` is **not** applied automatically; `npx supabase config push` is the intended route, and the sign-in code email template (`supabase/templates/code.html`, which must contain `{{ .Token }}`) must be confirmed in the dashboard because without it the email contains no code. Settings that matter: code length 6, expiry 600 s, minimum resend interval 60 s, site URL = the staging address, redirect allow-list = `https://<staging-address>/auth/callback/`.
6. Enable the Google provider in the dashboard with the client id and secret. In Google Cloud add the redirect address `https://<your-ref>.supabase.co/auth/v1/callback` (replace the placeholder) to the OAuth client.
7. Read the hosted **email send limit** and rate limits in the dashboard and record them in `SECURITY.md` section 12.2 (they differ from local).
8. Build and deploy, with the hosted values in the shell (not in a file):
   ```
   set NEXT_PUBLIC_SUPABASE_URL=https://<your-ref>.supabase.co
   set NEXT_PUBLIC_SUPABASE_ANON_KEY=<publishable or anon key>
   npm run deploy:staging
   ```
   (`set` is Windows `cmd`; in PowerShell use `$env:NAME = "value"`.) The script runs the guard, builds, writes the policy headers and the service worker, and publishes `out/` with `wrangler deploy`. **Verified so far:** the configuration (`wrangler deploy --dry-run` reads 85 files). **Not verified:** an actual deployment.
9. After deploying, check the headers with `curl -I https://<staging-address>/sign-in/` (expect `content-security-policy`, `x-content-type-options`, `no-cache`), run the manual Google checklist in `TESTING.md`, and run the end-to-end security tests' checks by hand on a phone.

## 5. Hosting behaviour the app relies on
- Pages are served at `/route/` with their security headers from `out/_headers` (generated; the content policy lists a hash for each page's inline scripts, so it must be regenerated on every build, which `npm run build` and `build:app` do).
- `sw.js` must be served with `Cache-Control: no-cache` (set in `_headers`), or users may keep an old worker.
- The service worker rewrites Next.js route-payload requests (`/dir/__next.a.b.txt`) to their exported paths. On the very first visit (before the worker controls the page) those prefetch requests return 404 on any static host; this is harmless and stops once the worker is active.
- Unknown addresses return the exported 404 page (`not_found_handling = "404-page"`).

## 6. Backup and recovery
- **Supabase Free has no automatic backups** (ZERO_BUDGET_REVIEW, Z-6). The destination for scheduled backups is decided in Phase 7.
- A manual copy of the database can be taken with `npx supabase db dump --linked -f backup.sql` (not yet exercised).
- **A restore has never been tested.** Under CLAUDE.md section 10, backups must not be called reliable until a restore drill has succeeded. That drill is mandatory before any real customer data.
- Because staging holds no real data, losing it costs nothing; production must not launch before the drill.
